# KerekTap — подключение к Kaspi (протокол биллера, онлайн)

ТОО «Power Solutions Company», БИН 191240014214
Сервис: **KerekTap** — заявки на услуги (спецтехника, вывоз мусора и др.)

---

## 1. Endpoint

```
https://kerektap.kz/api/kaspi/pay
```

HTTPS, порт 443. Метод — `GET`, параметры в строке запроса.
Ответ: HTTP 200 всегда, тело в JSON или XML (UTF-8). Время ответа — менее 1 с.

## 1a. Тестовый счёт

Для проверки на нашей стороне заведён постоянный счёт:

| Номер счёта | Сумма | Статус |
|-------------|-------|--------|
| **10000002** | 10000 ₸ | не оплачен, срок до 07.08.2027 |

Счёт `10000001` уже оплачен — на нём удобно проверить ответ «уже оплачен»
(код 3). Любой другой восьмизначный номер вернёт «не найден» (код 1).

## 2. Идентификатор абонента

**Номер счёта**, 8 цифр.

```
^[0-9]{8}$
```

Название поля для формы оплаты: **«Номер счёта»**

Счёт выставляет KerekTap и сообщает исполнителю в WhatsApp. Оплатить может
кто угодно — бухгалтер, родственник, с любого телефона: именно поэтому
идентификатор не привязан к номеру телефона плательщика.

## 3. Формат ответа

По умолчанию JSON. Переключается:

- параметром `&format=xml` или `&format=json`
- заголовком `Accept: application/xml`
- настройкой на нашей стороне, если удобнее зафиксировать один формат

В JSON номер оплаты отдаётся сразу под двумя именами — `prv_txn` и
`prv_txn_id`: в протоколе XML-пример называет это поле первым именем, JSON-
пример вторым.

## 4. Коды результата

| Код | Значение | Когда возвращаем |
|-----|----------|------------------|
| 0 | Успех | Счёт найден и не оплачен / платёж проведён |
| 1 | Не найден | Счёта с таким номером нет |
| 2 | Отменён | Счёт отменён или истёк срок оплаты |
| 3 | Уже оплачен | Повторная оплата того же счёта |
| 5 | Ошибка провайдера | Некорректные параметры, внутренняя ошибка |

## 5. Запрос `check`

```
GET https://kerektap.kz/api/kaspi/pay?command=check&txn_id=1234567&account=10000002&sum=0.00
```

Значение `sum` в `check` не обрабатывается (в протоколе оно фиктивное);
нужную сумму называем в ответе.

`txn_id` в `check` не обязателен — запрос без него отрабатывает так же.
Это сделано для удобства ручной проверки из браузера. В `pay` он обязателен:
это ключ, по которому мы отличаем повтор от нового платежа.

**Ответ, счёт найден (JSON):**

```json
{
  "txn_id": "1234567",
  "result": 0,
  "sum": "10000.00",
  "comment": "OK",
  "fields": {
    "field1": { "@name": "Исполнитель", "#text": "ТЕСТ — не рассылать" },
    "field2": { "@name": "Услуга", "#text": "Подписка на 30 дней" }
  }
}
```

**То же в XML** (`&format=xml`):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<response>
  <txn_id>1234567</txn_id>
  <sum>10000.00</sum>
  <result>0</result>
  <fields>
    <field1 name="Исполнитель">ТЕСТ — не рассылать</field1>
    <field2 name="Услуга">Подписка на 30 дней</field2>
  </fields>
  <comment>OK</comment>
</response>
```

**Счёт не найден:**

```json
{ "txn_id": "1234567", "result": 1, "comment": "Счёт не найден" }
```

**Счёт уже оплачен:**

```json
{ "txn_id": "1234567", "result": 3, "comment": "Счёт уже оплачен" }
```

## 6. Запрос `pay`

```
GET https://kerektap.kz/api/kaspi/pay?command=pay&txn_id=7654321&txn_date=20260807120005&account=10000002&sum=10000.00
```

**Ответ:**

```json
{
  "txn_id": "7654321",
  "prv_txn": "1041",
  "prv_txn_id": "1041",
  "result": 0,
  "sum": "10000.00",
  "comment": "OK"
}
```

`txn_date` сохраняем и используем для сверки взаиморасчётов — учёт ведём по
дате из запроса, а не по времени его получения.

## 7. Повторные запросы

Повтор `pay` с уже известным `txn_id` возвращает результат первой обработки
и **не проводит платёж второй раз**. Гарантируется уникальным индексом в базе.

## 8. Доступ

Протокол не предусматривает подписи запроса, поэтому endpoint принимает
запросы только с адресов Kaspi:

```
194.187.247.152
194.187.245.108
197.187.244.108
```

Запрос с другого адреса получает `result=5`.

**Уточнение:** третий адрес в протоколе указан как `197.187.244.108`, тогда
как первые два начинаются с `194`. Просим подтвердить, верен ли он —
на нашей стороне сейчас разрешены оба варианта.

Если у Kaspi есть отдельные адреса для тестового контура — пришлите, добавим.

Дополнительно готовы принимать постоянное значение в `data1` как общий
секрет, если это возможно настроить на вашей стороне.

## 9. Что проверено на нашей стороне

Сценарии прогнаны на боевом сервере, ответы соответствуют примерам выше:

- `check` по существующему счёту — код 0, сумма и реквизиты в `fields`
- `check` в XML — структура по протоколу
- `check` по несуществующему номеру — код 1
- `pay` — код 0, подписка продлена, `txn_date` сохранена для сверки
- повтор `pay` с тем же `txn_id` — тот же ответ, платёж НЕ проведён повторно
- `check` по оплаченному счёту — код 3

## 10. Вопросы к Kaspi

1. Подтвердить третий IP-адрес (см. п. 8).
2. Адреса тестового контура, если отличаются от боевых.
3. Сумму к оплате мы возвращаем сами в ответе на `check`. Если форма
   требует зафиксированного значения — сообщим окончательное перед
   запуском; цена подписки — 10 000 ₸ за 30 дней.
4. Ссылка на оплату услуги и **числовые идентификаторы полей** для неё —
   хотим отправлять исполнителю готовую ссылку вместе с номером счёта.
   Ожидаем вид `https://kaspi.kz/pay/<услуга>?service_id=…&<id поля>=<номер
   счёта>&<id поля>=<сумма>`. На нашей стороне это настройка, код менять не
   потребуется.
5. Комиссия 1,5% — подтвердить, удерживается ли она из суммы платежа
   (исполнитель платит 10 000 ₸, нам поступает 9 850 ₸) или начисляется сверх.
